## Exact reproduction order

1. Verify the assigned archive's hash before touching it (see above), then keep the raw
   evidence read-only for the remainder of the audit:
   ```
   chmod -R a-w evidence/
   ```
   This matches the submission contract's requirement to "keep source artifacts read-only" and
   the FAQ's explicit instruction to "keep the supplied pack read-only." All derived output
   (sample-manifest.csv, evidence-verdicts.json, the reports, evidence-index.csv) is written to
   the submission root, a separate location from the read-only `evidence/` directory, never
   back into it.
2. From the repository root, install dependencies:
   ```
   python3 -m pip install -r requirements.txt
   ```
3. Run the test suite (36 tests: 24 published fixtures; unit, negative, and malformed-input
   tests for the collector, sampler, and severity engine; a transfer-style fixture check;
   clean-state end-to-end tests for the audit engine; jsonschema validation against both
   published schemas; determinism and coverage checks for evidence-index.csv; and an
   end-to-end regression test that runs the full pipeline, including report generation, from a
   genuinely clean copy with no pre-existing generated files):
   ```
   python3 -m pytest tests/ -q
   ```
4. Run the audit engine against the published evidence with the assigned marker. This writes
   directly to the submission root (no separate staging directory), so there is never a
   forgotten "promote to root" step:
   ```
   cd audit-engine
   PYTHONPATH=. python3 -m engine.run_audit \
     --marker UBI-A7-ADFAFF62AD2E \
     --populations ../evidence/audit-populations.csv \
     --severity ../evidence/severity-rules.yaml \
     --outdir ..
   cd ..
   ```
   This regenerates `sample-manifest.csv`, `evidence-verdicts.json`, `audit-test-sheet.csv`,
   `nonconformity-register.csv`, and `evidence-index.csv` in place at the submission root.
   Re-running this command any number of times with the same marker produces byte-identical
   output apart from the `generated_at_utc` / `collection_time_utc` timestamp fields; I verified
   this with `tests/test_end_to_end.py` and `tests/test_evidence_index.py`.
5. Regenerate the two report PDFs from the frozen verdicts:
   ```
   python3 generate_reports.py
   ```
6. Verify the manifest after any change:
   ```
   find . -type f ! -name manifest.sha256 -print0 | sort -z | xargs -0 shasum -a 256 > manifest.sha256
   ```

## What I did not hardcode

The engine contains no candidate IDs, expected verdicts, sample IDs, or fixture case answers.
The severity engine reads its rule precedence and verdict text directly from
`evidence/severity-rules.yaml`; the sampler seeds from whatever marker is passed on the command
line, not a fixed value baked into the code. I verified this by running the same code against a
different marker in `tests/test_sampler.py`.

## Known limitation I want a reviewer to see before defense

I could not run the engine against the staff hidden or holdout fixtures, since they are not
distributed to candidates. `tests/test_transfer_style_fixture.py` is my own hand-written
stand-in, covering the same boundary conditions (exact threshold values, rule precedence when
multiple conditions are true at once) with different case IDs and values, to stress the same
logic the real holdout likely exercises. It is not a substitute for the real run.

## Test count: resolved by programme disposition

An earlier working draft of this submission produced eighteen test records, treating the
private overlay's instruction to expand A.5.18 into "two evidence requests" as license to
split six controls into two standalone test rows each. I identified a genuine conflict between
two of my own source documents: the hash-verified archive's `evidence/brief/brief.md` and its
`audit-test-sheet.csv` template both specify twelve tests, one per control, while the separate
assignment dashboard page referenced "eighteen" in five places. I escalated this discrepancy to
UBI programme support before submission. The disposition received: the hash-verified archive
governs; twelve tests, AT-01 through AT-12; the dashboard's "eighteen" references are legacy
wording; a single issued test may draw on multiple procedures, samples, or evidence items
internally, but remains one test. This submission implements that disposition: twelve issued
tests, with six controls (A.5.18, A.5.19, A.5.24, A.6.3, A.8.8, A.8.15) combining two evidence
requests internally into one test record each, via mechanical fact-merging (booleans OR'd,
counts summed) fed through the unchanged severity engine, not a hand-picked verdict. Full
reasoning is in `decision-log.md` D-002.
